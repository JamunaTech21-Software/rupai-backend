# Database: Prisma used SQL-first

**Part 3 of the spec is the authority on the schema.** `schema.prisma` is a typed mirror of it, and every migration's SQL is reviewed by hand. This is how the project uses Prisma without breaking the spec's rule that an ORM must never silently design the schema (Spec P2 §3.4, P3 §1.2, BACKLOG §2.1).

## Accounts

| Account                                     | Used by                               | Rights                                                                                                              |
| ------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `rupai_migrator` (`MIGRATION_DATABASE_URL`) | Prisma CLI only: `migrate`, `db seed` | DDL on `rupai` and `rupai_shadow`, `WITH GRANT OPTION`                                                              |
| `rupai_app` (`DATABASE_URL`)                | The running API and workers           | `SELECT`, `INSERT` database-wide. `UPDATE`, `DELETE` **per table, granted by the migration that creates the table** |

**Append-only by default.** MySQL cannot remove one table from a database-wide grant, so the app account starts with no `UPDATE`/`DELETE` anywhere and each mutable table is granted explicitly. Tables that must be immutable never get the grant, and the database itself refuses edits to them:

- `audit_change`, `status_history`, `access_log`, `integration_log`
- `stock_movement`, `journal_line`, `posting_link`, `payroll_component`
- the other immutable tables listed in Part 3

## Workflow for a schema change

```bash
npm run db:up                                   # local MySQL 8.4 (Docker)
# 1. Edit prisma/schema.prisma to mirror the Part 3 table(s) exactly.
npm run db:migrate:new -- --name p1_01_users    # 2. generates SQL only (--create-only)
# 3. Open prisma/migrations/<timestamp>_<name>/migration.sql and HAND-EDIT it:
#      - generated columns  (e.g. employment_profile.active_key, tea_lot.sold_key)
#      - CHECK constraints  (e.g. planted_area <= gross_area, quantity > 0)
#      - GRANT UPDATE, DELETE ON `<table>` TO 'rupai_app'@'%';   (mutable tables only)
#      - mark each edit with  -- HAND-EDIT: <why>
npm run db:migrate:dev                          # 4. apply locally
npm run db:drift                                # 5. must report "No drift"
npm run db:generate                             # 6. regenerate the client (also runs on npm install)
```

Production applies migrations with `npm run db:migrate:deploy`, under the migration account, after a backup (Spec P14 §5.3, §11.4).

**Never run `prisma db push`.** It would create tables without the hand-written constraints and grants. `npm run db:push` is deliberately blocked.

## Model conventions

| Concern                    | Rule                                                                                                                                                                                                                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Names                      | Models in PascalCase singular, mapped to the P3 snake_case table with `@@map("employment_profile")`. Fields in camelCase with `@map("employment_profile_id")`. The database keeps P3 names exactly                                                                                                                   |
| Surrogate keys             | `id BigInt @id @default(autoincrement()) @db.UnsignedBigInt`                                                                                                                                                                                                                                                         |
| ULID keys                  | The six field-capture tables only (P3 §2.2): `id String @id @db.Char(26)`, generated by the application                                                                                                                                                                                                              |
| Money                      | `Decimal @db.Decimal(18, 4)`                                                                                                                                                                                                                                                                                         |
| Quantity / weight          | `Decimal @db.Decimal(14, 3)`                                                                                                                                                                                                                                                                                         |
| Exchange rate              | `Decimal @db.Decimal(18, 8)`                                                                                                                                                                                                                                                                                         |
| Percentage / ratio         | `Decimal @db.Decimal(9, 4)`                                                                                                                                                                                                                                                                                          |
| States and enums           | `String @db.VarChar(30)` plus a TypeScript union and one runtime validator. **Never** a Prisma `enum` (P2 §2.6)                                                                                                                                                                                                      |
| Business dates             | `DateTime @db.Date`                                                                                                                                                                                                                                                                                                  |
| Timestamps                 | `DateTime @db.DateTime(0)`, always UTC                                                                                                                                                                                                                                                                               |
| Generated columns          | Declared in the model as optional and read-only (`/// GENERATED` doc comment), defined in the SQL. Never written from code                                                                                                                                                                                           |
| CHECK constraints          | SQL only. Prisma neither models nor drops them                                                                                                                                                                                                                                                                       |
| Index and constraint names | Use the P3 names (`ux_…`, `ix_…`, `fk_…`) via `map:`                                                                                                                                                                                                                                                                 |
| Floats                     | `Float` is never used anywhere                                                                                                                                                                                                                                                                                       |
| Rule tables                | Effective-dated policy tables (P3 §17) are created from `ruleTableSql` (`npx tsx scripts/rule-table-sql.ts <table> <method…>`), never written by hand, and registered in `src/modules/rule-tables.ts` so `tests/db/rules.test.ts` checks the block. Their model declares `specificity` and `active_key` as GENERATED |

`tests/fixtures/prisma-probe/` is a worked example of every rule above (generated column, CHECK, per-table grants, drift), and `npm run test:db` verifies it against real MySQL.

## Data access rules

- Inside services, use `withTransaction(db, async (tx) => …)` from `src/core/db/transaction.ts`. It runs at READ COMMITTED. Pass `tx` explicitly. Keep the transaction short.
- Contention points (stock balance, number sequences, receivable/payable allocation) lock rows with `lockRowsForUpdate(tx, table, where)`.
- Use parameterised `$queryRaw` for reports and very high-volume queries (P2 §8.4). Never interpolate user input into SQL. Identifiers go through `quoteIdentifier()`.

## Seeding

`npm run db:seed` runs the seeders registered in `prisma/seed/seeders.ts`, in order, each in its own transaction, as the migration account. Seeders use `seedRows(tx, table, key, rows)`, which inserts missing rows and updates changed ones by business code, so running it twice changes nothing. Statutory rules, the chart of accounts and posting rules ship **inactive** (P3 §31.3).
